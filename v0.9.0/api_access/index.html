Reading and writing a node

Getters and setters. Most take a node, which getnode gives you from an identifier; the ones that are asked for often take a workflow and an identifier as well.

Exported

Available after using MetidaFlows. These are the public API in the narrow sense: the names you cannot build or run a graph without. take! is here too, as a method on a Base function: Base puts the name in scope, so it needs no export.

MetidaFlows.getstatus — Function
getstatus(node::AbstractDataNode) -> Symbol
getstatus(model::Workflow, id::Int) -> Symbol

Return execution status of node.

Possible values:

  • :idle - created, never run;
  • :dirty - has to be computed;
  • :clean - ran, and its outputs are cached and can be republished;
  • :released - ran, and a consumer has since taken the value it produced through a handover port. The node has no cache for that port any more, so it recomputes on the next run exactly as a :dirty node would. For readiness, though, it counts as having produced: the consumer already has what it needs. The status is set during the consumer's execution, not the producer's. See PortSpec;
  • :executing - set by execute! for the duration of the call;
  • :failed - the node's own code raised;
  • :invalid_node, :invalid_settings, :invalid_result - a validation step refused it: execution_node_validation and validate_settings before the run, validate_result after.

A node that an invalidation reaches becomes :dirty whatever it was, so :released lives only until something downstream of it changes.

MetidaFlows.getinputdata — Function
getinputdata(node::AbstractDataNode, l::Symbol)
getinputdata(node::AbstractDataNode, l::Symbol, con::Int)

Read value from node input buffer.

The two-argument form depends on the port arity:

  • SinglePort: returns the buffered value, or nothing when the buffer is empty; more than one buffered value is an error.
  • MultiPort: returns a Vector of the buffered values, ordered by ascending connection id - that is, in the order the inputs were attached. The vector is freshly built, so a node may consume or reorder it without touching its own buffer. Use getinputconnections for the matching connection ids when a node needs to tell its producers apart.

The three-argument form returns the value written by connection con, or nothing when that connection has nothing buffered.

Both forms raise an error when l is not an input port of the node specification, and neither consumes or clears the buffer.

The value belongs to the graph, not to the node

Nothing is copied on a connection: what you get here is the same object the producer published and that every other consumer of that port received. A MultiPort builds a fresh vector, but the values inside it are the same objects.

So do not modify it in place. A node that sorts, scales or appends to what it was handed changes the producer's cached output as well, and the next run that does not recompute the producer - reset_mode = :none, or an execute! that pulls a :clean parent - will feed it the value it corrupted last time. The result is wrong and nothing reports it. Copy first, or declare the ports handover = true on both sides (see PortSpec) and consume the input with take!, which hands you ownership and makes working in place correct by construction.

Base.take! — Method
take!(node::AbstractDataNode, l::Symbol)

Read input port l and empty its buffer, so the value the node gets back is the only reference left to it.

This is how a node consumes an input declared handover = true in its NodeSpec, and it is the moment ownership actually moves: the value leaves the buffer, the engine notices and drops the producer's cached copy, and the node is left holding the only reference there is. From there it may sort, scale or append to it in place - the thing getinputdata must never be used for.

Declaring the ports is permission, not transfer. A consumer that keeps reading such an input with getinputdata changes nothing: the producer keeps its cache and stays :clean, and modifying what it read is the same mistake as anywhere else.

function MetidaFlows.execute_unsafe!(node::DataNode{Trim})
    table = take!(node, :table)        # теперь таблица наша
    filter!(row -> row.value > 0, table)
    setdata!(node, :out, table)
    return setreadyports!(node, :out)
end

Returns what getinputdata would: the value for a SinglePort, a Vector of values for a MultiPort, or nothing when nothing was buffered. A second call in the same execution finds the buffer empty and answers nothing, so take once and keep what you got.

The port has to be declared handover, and that is checked against the node's own specification - no graph needed. A connection into such a port is only allowed from a handover output, which is checked when the connection is created, so by the time a node takes anything the ownership is already established on both sides.

MetidaFlows.getinputconnections — Function
getinputconnections(node::AbstractDataNode, l::Symbol)

Connection ids buffered on input port l, ascending - the same order in which getinputdata returns the values of a MultiPort.

Needs no Workflow, so it is callable from execute_unsafe!, which is given only the node. The ids are what a node zips against its values when it has to tell its producers apart:

for (cid, v) in zip(getinputconnections(node, :ins), getinputdata(node, :ins))
    # settings[:role][cid] - the meaning the graph author assigned at build time
end

Raises an error when l is not an input port of the node specification.

See bufferkeys for how a custom buffer container reports its order.

MetidaFlows.setsettings! — Function
setsettings!(model::Workflow, id::Int, settings::Dict{Symbol, <: Any}; replace = false)

Apply new node settings and invalidate dependent nodes.

Settings are applied using setsettings_unsafe!, or replacesettings_unsafe! when replace = true, after which the target node and all downstream nodes are invalidated via invalidate_downstream!.

Notes

  • This function is the safe high-level entry point for mutating node configuration inside a workflow.
  • Settings are merged by default: only the keys present in settings are overwritten, the rest are kept. replace = true makes settings the whole configuration instead, dropping every key it does not mention - the only way to remove a setting, and what restoring a saved version needs.
  • replace = true is recorded in the change log, so a reader can tell which of the two a SettingsChanged record meant.
  • The keys are not checked against the list in NodeSpec: that list is a declaration, and an unknown key is simply stored. Enforce what matters in validate_settings.
  • model.ver is not raised: it versions the graph's structure, and four cached values hang on it. Settings change what a node computes, not what the graph looks like, so raising it would throw away the topological sort and the readiness map for nothing. Invalidation, not the version, is what makes the node recompute.
  • An undeclared key is stored but not written to a snapshot: settings_to_dict writes only the declared ones. So a setting kept off the list lives for as long as the object does and no longer, which is the one place where the asymmetry has a consequence.

Returns

The node.

Public, not exported

Part of the public API, reached as MetidaFlows.name or brought in with import MetidaFlows: name. They are documented, and a breaking change to one of them moves the version exactly as a change to an exported name does. They are simply not put in your namespace, either because you add methods to them, because they are needed rarely, or because the name is too general to take over.

MetidaFlows.getexecn — Function
getexecn(model::Workflow, id::Int) -> Int

How many times the node has executed since its execution state was last cleared.

The counter lives in NodeState and is raised by execute! just before the node's own code runs, so a node that raised still counts as having executed. It is zeroed at reset level :soft and above, which covers reset! as called by default and reset_mode = :soft of scheduler!; :status and :none leave it standing, so reset_status! keeps the count.

This is the cheapest way to ask what a run actually did: a node left :dirty below a failure has the same status as a node that was never reached, but a different exec_n. In a cyclic ABW workflow it counts turns.

Example

scheduler!(w)
getexecn(w, id)                 # 1 — узел исполнился один раз
scheduler!(w; reset_mode = :none)
getexecn(w, id)                 # 1 — чистый узел не пересчитывался

MetidaFlows.bufferkeys — Function
buffervalues(buffer)  -> Vector
bufferkeys(buffer)    -> Vector{Int}
buffersingle(buffer)

How the engine reads one port's buffer. The three are what a container may specialize, and PortBuffer - the default - specializes all three.

buffervalues and bufferkeys give the values and the connection ids ordered by ascending connection id; they are what getinputdata and getinputconnections return for a MultiPort, so the two line up position for position. buffersingle gives the one buffered value of a SinglePort, nothing when the buffer is empty, and raises when more than one connection has written - the generic form reaches it through the pair the iterator yields, which is worth avoiding in a container that stores its values contiguously (measured: a 200-node SinglePort chain runs 20 % faster for it).

The default works for any container keyed by connection id: it collects the keys, sorts them, and indexes. That is two allocations and a sort on every call, because a Dict cannot report an order it does not keep.

A container that does keep its keys in order can say so, and then the sort and one of the allocations go away:

MetidaFlows.bufferkeys(b::SortedBuffer)   = copy(b.cids)
MetidaFlows.buffervalues(b::SortedBuffer) = copy(b.vals)
MetidaFlows.buffersingle(b::SortedBuffer) = length(b.vals) == 1 ? b.vals[1] :
                                            isempty(b.vals) ? nothing :
                                            error("Multiple connections in single port")

Both must return a fresh vector in the same order: the node is free to sort, consume or empty what it is given, and must not reach the buffer through it. Returning b.vals itself would hand the engine's buffer back to the node.

MetidaFlows.getportconnections — Function
getportconnections(model::Workflow, id::Int, label::Symbol; direction = :both)

Return all connections attached to a specific port, as a Vector{NodeConnection}.

direction selects the side the label is read on:

  • :input - incoming connections whose input_port is label;
  • :output - outgoing connections whose output_port is label;
  • :both - the incoming ones first, then the outgoing ones. A node may carry the same label on an input and on an output port, and then :both returns both sets in one vector; getinputconnections is the narrower question when only the input side matters.

Within each side the order follows the node's connection index, which refreshind! keeps ascending.

An unknown node id raises a KeyError, any other direction an error.

MetidaFlows.setreadyports! — Function
setreadyports!(node::AbstractDataNode, labels::Symbol...) -> Vector{Symbol}
setreadyports!(node::AbstractDataNode, labels) -> Vector{Symbol}

Record which output ports the current execution published, in the node's own storage, and return that storage.

This is what a node returns from execute_unsafe! instead of building a label vector:

function MetidaFlows.execute_unsafe!(node::DataNode{Doubler})
    setdata!(node, :out, 2 * getinputdata(node, :in))
    return setreadyports!(node, :out)          # instead of return [:out]
end

The vector belongs to the node and is reused, so from the second execution on the label list costs nothing. Measured on a chain where every node publishes one port: 175 bytes per node per run against 111 at a thousand nodes, 219 against 155 at ten thousand. The run itself gets about 4 % faster - the saving is allocation, not arithmetic.

Returning a vector built in the node - return [:out] - keeps working and means the same thing. The engine stores it through this same function.

With no labels it records that the execution published nothing, which is what a gate that did not fire returns:

return setreadyports!(node)                    # instead of return Symbol[]

The labels are checked, which is the one difference

Every label passed to the varargs form has to be an output port of the node's NodeSpec; one that is not raises. The call sits in the node's own code, so the engine catches it, the node ends :failed, and the message in model.log names the label.

Returning a vector instead leaves the labels on trust: a label that was never written, or is not an output port at all, ends the node :clean and its consumer silently gets nothing - a symptom that shows up one node downstream. That is the reason to prefer this function over a vector even where the allocation does not matter.

The collection form does not check, because it is also how the engine stores what a node returned: by that point the value has already come back from user code, and raising there would escape the run instead of marking the node.
