Graph and nodes

Building and editing a graph, the graph cache, invalidation, readiness, the node containers and the node register.

Exported

Available after using MetidaFlows. These are the public API in the narrow sense: the names you cannot build or run a graph without. replace! is here too, as a method on a Base function: Base puts the name in scope, so it needs no export.

MetidaFlows.add_connection! — Function
add_connection!(model::Workflow, c::NodeConnection; id = 0)
add_connection!(model::Workflow, id_out::Int, port_out::Symbol, id_in::Int, port_in::Symbol; id = 0)

Add connection to workflow.

Performs:

  • connection validation (check_connection_validity),
  • connection registration under a new or a given identifier,
  • incoming/outgoing index updates,
  • invalidation of the consumer and everything below it,
  • a ConnectionAdded record in the change log,
  • a raise of model.ver.

If the source node already has status :clean, its output data is immediately propagated into the target node input buffer.

Identifier

id names the identifier to insert under; 0, the default, takes the next free one. The rules are add_node!'s: an identifier in use is refused, an explicit one raises the counter.

It matters more here than it does for a node. A MultiPort input orders its values by ascending connection identifier, so restoring a graph with the identifiers it was saved with restores that order as well - while renumbering could reorder the inputs of a node that nobody edited.

Returns

Assigned connection identifier (Int).

MetidaFlows.add_node! — Function
add_node!(model::Workflow, node::AbstractDataNode; reset = :full, id = 0)

Add node to workflow.

Assigns a node identifier and registers the node in workflow storage. Identifiers come from a monotonically increasing counter and are never reused.

Identifier

id names the identifier to insert under; 0, the default, takes the next free one. An explicit identifier is refused when it is already in use, and it raises the counter, so later automatic insertions keep clear of it.

This is what lets a server apply the difference between two saved versions to a live graph instead of rebuilding it: the nodes it does not touch keep their identifiers, their cached results and their :clean status, and the change log stays one continuous sequence. Rebuilding would renumber everything and throw all of that away.

Notes

A node whose status is neither :idle nor :clean is reset on insertion, at reset, which is one of RESET_LEVELS. The default :full drops the results of whatever the node did before and keeps its settings, so a node may be configured before or after it joins the workflow. A freshly created node and an already computed node are inserted unchanged.

Pass reset = :all to empty the node on insertion, which is what versions before 0.5.0 did unconditionally, or reset = :none to insert it exactly as it is.

Insertion raises model.ver and writes a NodeAdded record to the change log.

Returns

Assigned node identifier (Int).

Base.replace! — Method
replace!(model::Workflow, node::AbstractDataNode, id::Int; throw_warn = true) -> AbstractDataNode

Put node into the workflow under the identifier id, keeping every connection, and return the node that was displaced.

This is what delete_node! followed by add_node! cannot do: deleting a node deletes its connections, so the wiring - and the connection identifiers that order a MultiPort - would have to be rebuilt. Here the graph keeps its shape and only the node at that one identifier changes, so the nodes the replacement does not reach keep their cached results and their :clean status.

What is checked, and all of it before anything is written

Two things come first: the identifier has to exist, and node must not already be in the workflow under another identifier - the same object under two keys would be one node pretending to be two. Replacing a node with itself is allowed, and amounts to the invalidation alone.

Every connection that touches id must still be valid with the new node in place, by the same rules add_connection! applies when a connection is created:

  • the port each connection names exists on the replacement, on the right side;
  • datatypes line up: the producer's output type is a subtype of the consumer's input type, in both directions;
  • a handover output that is connected has exactly one connection, and a handover input is fed only by a handover output - checked from both sides, so neither a taking consumer nor a handing producer can be left paired with an ordinary port;
  • an input port that is not a MultiPort has exactly one incoming connection;
  • a :terminal output that is connected warns, as it does at creation (throw_warn = false silences it).

A node connected to itself - a :feedback loop - is checked with the replacement on both sides of that connection, which is what it will be.

Order of operations

  1. the checks above;
  2. the old node's settings are written onto the replacement, key by key - keys the old node does not have are left as the replacement brought them. This happens before the swap, so a settings container that refuses a key (a typed container missing a field, a field of another type) fails with the graph still untouched;
  3. the replacement takes the identifier, the editor position of the node it displaces and the place in the workflow, and is marked :dirty - always, whatever it arrived as;
  4. its input buffers are filled from parents that have already published - :clean and the port among their ready_ports, the rule the engine itself uses - so the replacement can run without recomputing anything above it. A :released parent is skipped: it no longer holds what it handed over;
  5. the consumers below are invalidated: each child's buffer slot fed from id is cleared and the invalidation propagates;
  6. model.ver is raised and the change is recorded in the change log.

Should anything in steps 3-6 throw, the old node goes back and model.ver returns to what it was. An invalidation that had already propagated is left alone: a node marked :dirty only costs a recomputation.

The replacement always ends up :dirty

Whatever the node arrived as, it is marked :dirty: the replacement has not run here, and results it may be carrying from somewhere else belong to other settings and another graph. So a replacement always recomputes on the next run, and so does everything below it. mark_dirty! also drops its data and its ready_ports, so nothing it brought with it can be published as if this graph had produced it.

What survives is the part that makes the replacement cheap: the input buffers are filled from parents that already published, so the nodes above are not recomputed. That is the whole point of replacing in place.

The identifier and the position belong to the slot

Both are taken from the node being displaced, and whatever the replacement arrived with is discarded: the connections stayed, so to anyone looking at the graph this is the same node in the same place, with different behaviour. A replacement that is meant to sit somewhere else is moved with setposition! after the call.

The change log gets a NodeReplaced(id, type, previous) record, so one line says what became what. That record exists only in snapshot format 3 and later.

Example

new = DataNode(FasterFilter, filter_spec())
old = replace!(w, new, 7)            # node 7 is now FasterFilter, wiring intact
scheduler!(w; reset_mode = :none)    # only node 7 and below recompute

See also add_node!, delete_node!, add_connection!.

Public, not exported

Part of the public API, reached as MetidaFlows.name or brought in with import MetidaFlows: name. They are documented, and a breaking change to one of them moves the version exactly as a change to an exported name does. They are simply not put in your namespace, either because you add methods to them, because they are needed rarely, or because the name is too general to take over.

MetidaFlows.replacespec! — Function
replacespec!(model::Workflow, id::Int, spec::NodeSpec; throw_warn = true) -> AbstractDataNode

Give node id a different NodeSpec, keeping its type and every connection, and return the node that was displaced.

A node's spec is an immutable value that nodes share: building two nodes from one NodeSpec object is legal, and dict_to_workflow does exactly that - every node of a type loaded from a snapshot gets the one spec object held in NODE_REGISTER. So assigning into spec.input_ports or spec.output_ports does not change one node's ports: it changes them for every node sharing that spec, for the register, and therefore for every workflow loaded afterwards in this process. This function is how a node's ports change instead.

It is replace! with a node built for you, so everything that holds there holds here: the connections are re-checked against the new spec before anything is written, the old node's settings and its position move onto the new one, the input buffers are filled from parents that already published, the consumers below are invalidated and model.ver is raised. The change log gets a SpecChanged record rather than a NodeReplaced one, because the node type does not change here.

A side effect worth having on its own: the node comes out holding the spec you passed, so a node loaded from a snapshot stops sharing the register's.

To survive a snapshot, the interface needs a declared key

A snapshot names a node by a key from NODE_REGISTER, not by its ports, so an interface that is declared nowhere cannot be named: the node comes back with the ports of its type, and workflow_to_dict warns about it. Declare the variant once, where the node types themselves are declared:

function __init__()
    register_node!(DataNode(Scale, scale_spec()))
    register_node!(DataNode(Scale, wide_spec()); key = "Main.Scale@wide")
end

After that any node of that type whose spec describes the same interface is named by that key - noderegkey matches by interface, so it makes no difference whether the spec object is the registered one, a copy of it, or one replaceport! built on the spot:

replacespec!(w, 7, wide_spec())      # своя копия той же формы
noderegkey(getnode(w, 7))            # "Main.Scale@wide"

What not to do is register a session's own copy under a key that is already taken: overwrite would hand the entry to that copy, and every node of the interface registered before it would stop being named at all, in this workflow and in every other one in the process.

See also replaceport!.

MetidaFlows.replaceport! — Function
replaceport!(model::Workflow, id::Int, ps::PortSpec, direction::Symbol; throw_warn = true) -> AbstractDataNode

Change one port of node id - direction is :input or :output - and return the node that was displaced.

The port is matched by ps.label: a label the node already has on that side is replaced, a label it does not have is added. The rest of the spec is carried over, and a fresh NodeSpec is built rather than the old one edited, for the reason replacespec! explains. To remove a port, build the spec yourself and call replacespec!.

Everything a changed port could break is refused before anything is written, by replace!'s rules: a narrowed datatype that an existing connection no longer satisfies, a MultiPort input turned SinglePort while two connections feed it, a handover output that has more than one consumer, and either side of a handover pair left facing an ordinary port.

#  Тот же порт, но тип уже: пройдёт, только если связи сходятся
replaceport!(w, 7, PortSpec("In", Float64, :in), :input)

The spec is built here, so the node ends up with a spec object of its own. For a snapshot that is not what matters: noderegkey matches a node against NODE_REGISTER by interface, so the port change survives a file as long as the shape it produces is declared under some key. If it is not, workflow_to_dict says so and the node comes back with the ports of its type.

So declare the shapes a graph editor can produce once, for the process, as replacespec! shows. Registering the node here instead would put a per-session copy under a process-wide key, and that takes the key away from every other graph that uses it.

See also replacespec! and noderegkey.

MetidaFlows.initbuffer! — Function
initbuffer!(buffer, spec::NodeSpec)

Prepare an input buffer against the node specification, and return it.

Called by the DataNode constructor. Two things have to hold afterwards: every entry of buffer names a declared :input port, and every declared :input port has an entry - the engine indexes buffer[label] without checking.

How the second is achieved depends on the container, which is why this is a function and not a loop in the constructor:

  • a dictionary is grown: a missing port gets a fresh empty entry of the dictionary's own value type, so Dict{Symbol, PortBuffer{Any}} keeps giving PortBuffer{Any} and a typed Dict{Symbol, PortBuffer{Float64}} keeps giving PortBuffer{Float64};
  • a struct (AbstractNodeFields) is checked: fields cannot be added, so a port without a field is an error naming the field to declare.

Define a method for a container that is neither.

Example

mutable struct PairBuffer <: MetidaFlows.AbstractNodeInputBuffer
    a::PortBuffer{Float64}
    b::PortBuffer{Float64}
    PairBuffer() = new(PortBuffer{Float64}(), PortBuffer{Float64}())
end
MetidaFlows.nodebuffer(::Type{MyNode}) = PairBuffer()

MetidaFlows.nodebuffer — Function
nodesettings(::Type) -> container
nodedata(::Type)     -> container
nodestate(::Type)    -> container
nodebuffer(::Type)   -> container

Fresh containers for a node of the given node type. These are the defaults of the DataNode keyword constructors and what dict_to_node builds a loaded node with, so one method here types a node everywhere - by hand, in a graph, and after a round trip through a snapshot.

Default: Dict{Symbol, Any}() for settings and data, NodeState for state, Dict{Symbol, PortBuffer{Any}}() for the input buffer. Each is called once per node, and only when the corresponding keyword is not given, so a container is never built and thrown away.

mutable struct ScaleSettings <: MetidaFlows.AbstractNodeSettings
    factor::Float64
    ScaleSettings() = new(1.0)
end
mutable struct ScaleData <: MetidaFlows.AbstractNodeData
    out::Union{Float64, Nothing}
    ScaleData() = new(nothing)
end

struct Scale <: AbstractNodeType end
MetidaFlows.nodesettings(::Type{Scale}) = ScaleSettings()
MetidaFlows.nodedata(::Type{Scale})     = ScaleData()
MetidaFlows.nodebuffer(::Type{Scale})   = Dict{Symbol, PortBuffer{Float64}}()

node = DataNode(Scale, spec_scale())
# DataNode{Scale, ScaleSettings, ScaleData, NodeState, Dict{Symbol, PortBuffer{Float64}}}

Specialize them independently: typed settings with Dict data is a perfectly good combination.

nodebuffer chooses the buffer container, so all three levels of it are yours: the outer mapping from port label to buffer (a Dict or a struct with one field per input port), the per-port container keyed by connection id, and the value type. A value type narrower than Any is checked on every write, which is how a port carrying the wrong type is caught early.

MetidaFlows.nodebuffer(::Type{Scale}) = ScaleBuffer()   # <: AbstractNodeInputBuffer

See AbstractNodeFields for what a container struct has to provide, initbuffer! for how it is checked against the spec, and buffervalues for teaching a per-port container to report its own order cheaply.

MetidaFlows.register_node! — Function
register_node!(node::DataNode; key = nodetypestr(node), overwrite = false, skipmode = false) -> String | Nothing
register_node!(model::Workflow; overwrite = false, skipmode = false, throw_warn = true) -> Vector{String}

Register the type and the specification of a node in NODE_REGISTER, so that a snapshot naming it can be restored. Returns the key, which is nodetypestr of the node unless key says otherwise.

Registering anything under a key already taken raises; overwrite replaces the entry, skipmode returns nothing instead of raising.

key is what makes a second specification of one type registrable: the same T, another NodeSpec, its own key. That is what a node needs to survive a snapshot after replacespec! or replaceport!, because a snapshot carries a key and not the ports themselves - see noderegkey and workflow_to_dict.

register_node!(DataNode(Scale, scale_spec()))                        # "Main.Scale"
register_node!(DataNode(Scale, wide_spec()); key = "Main.Scale@wide")

A key names an interface, not an object, and it is declared once for the process. NODE_REGISTER is one table for every workflow, and noderegkey matches a node against it by interface, so a graph that later builds the same shape - a copy of the spec, a deepcopy, a replaceport! that happens to produce it - is named by the key that is already there and needs no registration of its own. Declare the variants alongside the node types, from __init__ or at startup.

What not to do is register a session's own copy under a key that is taken. Without overwrite that raises; with it, the entry becomes this copy, and if its interface differs then every node that held the previous one stops being named by any key - in this graph and in every other one in the process. A differing overwrite therefore warns, and throw_warn = false silences that.

The Workflow form registers every node type of a graph and returns the keys it added, sorted. A graph normally holds several nodes of one type, and that is not a repeated registration: each type is registered once per call, from its lowest-numbered node, and the remaining nodes of that type are passed over. So register_node!(w) is the ordinary call, and the flags mean for a graph exactly what they mean for a node - what to do about a key that was already taken before this call. A type whose spec has changed is the case for overwrite = true; skipmode = true keeps whatever is registered.

Which node of a type is registered used to be a matter of model.nodes iteration order, and that order is machine-dependent. It mattered from the moment replacespec! made it possible for two nodes of one type to hold different specs - so the walk goes by ascending id, and a graph where nodes of one type disagree about their spec is reported: the types are named, with the node the spec was taken from and the nodes left out. throw_warn = false silences that.

Register from `__init__`, not at top level

A package that registers its nodes in top-level code loses the registration: the call runs while that package is precompiled, and a mutation of another module's global state is not captured in the precompiled image. At load time top-level code no longer runs, so the register stays empty - with no error at all.

module AcmeNodes
using MetidaFlows
struct FancyFilter <: MetidaFlows.AbstractNodeType end
fancy_spec() = NodeSpec("Fancy filter", PortSpec[], PortSpec[], [:column])

function __init__()
    MetidaFlows.register_node!(DataNode(FancyFilter, fancy_spec()))
end
end

MetidaFlows.log! — Function
log!(model::Workflow, msg::LogMsg)

Append msg to model.log if SETTINGS[:logging] is on, and return the model. The single place the log is written.

The log is bounded by SETTINGS[:log_limit], and the engine never clears it between runs, so what it holds is the most recent log_limit messages of this workflow's whole life. Both the switch and the bound live in SETTINGS, not in the workflow.

Unlike this one, the graph change log is never capped - see AbstractAuditEvent for why an edit history with holes in it is worse than none.

source
log!(node::AbstractDataNode, msg::LogMsg)
log!(node::AbstractDataNode, level::Symbol, message::AbstractString)

Append a message to this node's own log, node.state[:log], and return the node.

This is the log a node writes about itself, for whoever is looking at that node - "read 1 240 rows", "3 values dropped as missing", "converged after 11 iterations". execute_unsafe! is handed only the node, which is exactly what this needs, so a node can report from inside its own run:

function MetidaFlows.execute_unsafe!(n::DataNode{ReadCSV})
    tbl = CSV.read(n.settings[:file], DataFrame)
    log!(n, :info, "read $(nrow(tbl)) rows")
    setdata!(n, :table, tbl)
    return [:table]
end

Who writes, and who switches it off

Nothing in the engine writes here: engine messages go to Workflow.log through log!(model, msg). That is also why this one has no on/off switch where Workflow.log has logging - the only thing that writes a node's log is the node's own code, so declining to call this is the switch.

Bound and lifetime

The log keeps the most recent SETTINGS[:log_limit] messages, oldest dropped first; the default is 1000, and 0 means no limit. That bound is what makes logging from inside a cycle safe: a node that writes a line on every turn of a 100 000-turn loop ends up holding log_limit records, the last ones written.

The log belongs to a run. execute! empties it whenever the workflow's run_id is not the one the node last saw, and it does so before anything else

  • before the :clean check, so a node the engine takes up and then skips comes

out with an empty log just the same. After a scheduler! call a node therefore holds the messages of that run and nothing older; only a node the scheduler never called execute! on at all, because it was not ready or was never enqueued, keeps what it had.

Otherwise it is cleared only by empty!(node.state) and by reset! at level = :all, the level that empties a node completely. :full and below leave it alone, and so does add_node!, whose default reset is :full.

A custom AbstractNodeState needs a log field to be written to, and a node whose state has none raises an error naming the type. The bound is read from SETTINGS in either case, so a state container has nothing to declare for it.

MetidaFlows.reset! — Function
reset!(model::Workflow; level::Symbol = :full, soft::Bool = false)

Reset every node of the workflow to level, which is one of RESET_LEVELS.

The default :full is an invalidation, not a wipe: statuses become :dirty, cached output data, ready_ports and the buffers of :feedback ports are dropped, and settings survive. Reach for :all to empty a node completely, and for :inputs when the input buffers have to go but the configuration does not.

reset!(model; level = L) is exactly a loop of reset!(node; level = L) over the nodes: the two scopes mean the same thing at the same level, including the default.

soft = true is the older spelling of level = :soft and still works.

This is the only place where exec_n is zeroed for the whole workflow, so the counter measures work done since the last reset! rather than since the last invalidation - mark_dirty! leaves it alone on purpose.

Returns

The workflow.

source
reset!(node::AbstractDataNode; level::Symbol = :full, soft::Bool = false)

Reset one node to level, which is one of RESET_LEVELS.

The default is :full, the same as for a workflow: an invalidation that keeps the settings. Before 0.5.0 reset!(node) meant :all and emptied the node including its configuration; write level = :all where that is what you want.

level = :all sets the status to :idle rather than :dirty, because a node with nothing in it has not been invalidated, it has been emptied - that is the level for reusing a node object.

soft = true is the older spelling of level = :soft and still works.

mark_dirty! is not a level of this ladder: it is the primitive the engine propagates invalidation with, and it keeps exec_n and the stop flag that :soft already clears.

Returns

The node.

MetidaFlows.RESET_LEVELS — Constant
RESET_LEVELS

How much reset! throws away, from nothing to everything, in order. Each level does what the one before it does and more:

levelclears, on top of the level beforekeeps
:nonenothingeverything
:statusthe status, which becomes :dirtyeverything else
:softexec_n, the stop flagdata, ready_ports, every buffer, settings
:fullcached output data, ready_ports, the buffers of :feedback portssettings, the other buffers, the node log
:inputsevery remaining input buffersettings
:allsettings, the node log, execution_id; the status becomes :idlenothing - the node is as new

The same words name the reset_mode of scheduler!, which accepts three of them - :none, :soft and :full - and raises on the rest.

Clearing the feedback buffers at :full is what makes a full reset full for a cyclic workflow: those buffers hold the state of the last turn, and a loop head that still finds it there resumes the previous run instead of starting a new one. :soft keeps them on purpose - that is how state is carried between scheduler! calls.

:full and :inputs split the buffers between them, so :inputs is the level that leaves none behind.

MetidaFlows.mark_dirty! — Function
mark_dirty!(node::AbstractDataNode; soft::Bool = false)

Invalidate node execution result.

Performs the following operations:

  • sets node status to :dirty,
  • clears ready_ports,
  • clears cached output data stored in node.data.

With soft = true the last two steps are skipped: only the status changes, and ready_ports and node.data are left in place. That is what reset_mode = :soft of scheduler! uses to keep results between runs.

This function intentionally does not clear:

  • node settings,
  • input buffers,
  • execution logs,
  • execution counters and the rest of the state.

That last line is why mark_dirty! is not a level of RESET_LEVELS: :soft, which throws away less in every other respect, already zeroes exec_n and the stop flag. This function is the primitive invalidation propagates with - see invalidate_downstream! - and losing the count of a subtree that was merely invalidated would be wrong.

Returns

The node.

MetidaFlows.request_stop! — Function
request_stop!(node::AbstractDataNode, flag::Bool = true)

Ask the scheduler to end the run as soon as this node finishes.

Called from inside execute_unsafe! by a node that knows there is nothing left worth computing - a search that found its answer, a check that failed a precondition. What the node publishes is published as usual, so a result can travel out through a :terminal port in the same execution; what changes is that nothing more is executed.

function MetidaFlows.execute_unsafe!(n::DataNode{Found})
    setdata!(n, :answer, getinputdata(n, :in))
    request_stop!(n)
    return [:answer]
end

Both schedulers honour it: ABW stops serving the queue and DAW leaves the topological traversal. Nodes that were queued or still ahead in the order are not executed and end the run :dirty, exactly as they do below a failure - a stop is not a failure, so failed_nodes stays empty and strict does not raise. The scheduler appends an :info record to model.log naming the node that stopped it.

The flag lives in the node's NodeState and is cleared by reset! at :soft or above, so the next run starts clean. With reset_mode = :none nothing is reset, so a stop requested by an earlier run is still there and the next one ends on that node again.

A node whose state is a custom AbstractNodeState cannot carry the flag: this is defined on NodeState and raises for every other state, naming the type. A stop field of your own does not help, because nothing dispatches on a field. Asking isstoprequested about such a node answers false instead, because a stop that cannot be requested has not been.

Which node stopped a run is an ordinary query afterwards:

[id for (id, n) in w.nodes if isstoprequested(n)]

See also isstoprequested.

MetidaFlows.isstoprequested — Function
isstoprequested(node::AbstractDataNode) -> Bool

Whether request_stop! was called on this node and not yet cleared, either by request_stop!(node, false) or by reset! at :soft or above. A node whose state is a custom AbstractNodeState always reports false: the flag is a field of NodeState, and nothing else can carry it, so a stop can never be requested by accident.

scheduler!(model; reset_mode = :none) resets nothing, so a stop raised in an earlier run is still raised: that run ends at the same node again. Lower the flag with request_stop!(node, false) when that is not what you meant.

MetidaFlows.isready — Function
isready(model::Workflow, id::Int; wait_optional::Bool = true)

Check whether a node is ready for execution.

A node is ready when, for every connection entering a :normal input port, the producer has produced and, if the port is required, that producer actually published to the port this connection leaves. Connections entering ports of any other kind are not waited for.

"Has produced" is :clean or :released - see hasproduced. A producer whose value was taken through a handover port has no cache left, but the consumer already holds what it needs, so readiness cannot treat it as unfinished.

The kind asymmetry is what makes cycles possible: a :feedback edge carries the value of the previous iteration, so requiring its producer to have produced would deadlock - the node would wait for a producer that waits for the node.

The publication condition is what makes conditional evaluation work. A node that publishes only some of its output ports - every gate in the package does this - leaves the others with no value at all, and invalidate_unpublished! clears the consumer buffers so that nothing of the previous turn is read in their place. A consumer whose port is required therefore is not ready and does not run, in either scheduler; one whose port is required = false is ready and reads nothing, which is where a condition can be acted on.

wait_optional

An optional port's producer is waited for by default, and that wait is not about the value - it is what separates "the producer published nothing" from "the producer has not run yet". Both read nothing, and only the first one is an answer.

With wait_optional = false an optional port stops contributing to readiness altogether: a producer that has not produced is read as absent instead of being waited for. That is only sound where the producer has already had its chance to run, so this is not something to set by hand - it is what scheduler!(model; release_optional = true) uses, in the one place each scheduler can guarantee it. Required ports are unaffected.

A node released this way may still be holding an earlier turn's value in the optional port's buffer, which invalidate_stale_optional! clears.

Notes

  • Current node status itself is not checked.
  • A port with no connection at all is a different case: this function walks connections and cannot see such a port. Completeness of required buffers is validated separately by execution_node_validation, which both schedulers enable: such a port makes the node :invalid_node.
  • A node with :normal input ports but no incoming connection is ready immediately; it just never gets enqueued unless something feeds it.

MetidaFlows.makegraph — Function
makegraph(model::Workflow)

Directed graph representation of workflow: node identifiers become vertex names and each connection adds an edge from its producer to its consumer.

Built once per structural change and kept in model.graph; a call that finds the cache current does no work at all. See GraphCache.

Returns

The shared graph held by the workflow. Treat it as read-only: adding a vertex or an edge to it would leave the workflow describing a graph it does not have, and nothing would report that. Make a copy before modifying one.

Notes

All connections are included regardless of the kind of the ports they attach to. A :feedback edge is therefore an ordinary edge here, so a graph with a feedback loop is cyclic and scheduler! for a DAW workflow rejects it. That is by design: cycles are an ABW feature.

The graph is simple and carries no port labels, so two connections between the same pair of nodes give one edge and the edge count is not the connection count. Reach for find_connections when the connections themselves are needed.

A graph edited around the editing functions is not seen here - see Editing the graph in Workflow.

Graphs.is_cyclic — Method
is_cyclic(model::Workflow) -> Bool

Whether the workflow's graph contains a cycle, from the same cache as makegraph; see GraphCache.

A cycle must be closed through a port declared kind = :feedback to be executable, and only by ABW: scheduler! on a DAW workflow rejects a cyclic graph. The port's kind is not consulted here - makegraph builds an edge per connection whatever the kind, so a feedback edge is an ordinary edge and the graph it closes is cyclic.

Graphs.topological_sort — Method
topological_sort(model::Workflow) -> Vector{Int}

A topological order of the workflow's nodes, from the same cache as makegraph; the order scheduler! traverses a DAW workflow in. See GraphCache.

Returns

The shared order held by the workflow, as node identifiers. Treat it as read-only.

Notes

Which of several valid topological orders this is, is unspecified: it follows the order the vertices went into the graph, which is dictionary order. It is the same for as long as the structure is unchanged.

A cyclic graph has no topological order and this raises, as it does on a bare graph - ask is_cyclic first. Unlike the other three cached values, a failure caches nothing, so every call on a cyclic graph raises again.

Example

for id in topological_sort(w)
    execute!(w, id)
end
