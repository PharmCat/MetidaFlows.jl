Execution model

How a node moves between statuses, what invalidation does and does not recompute, and what each of the two schedulers guarantees. The user guide introduces the pieces; this page is the model they follow.

Statuses and the execution lifecycle

StatusMeaning
:idlefreshly created, never executed, no settings applied
:dirtyneeds (re)computation
:executingcurrently running - also used to detect re-entry
:cleanup to date, outputs cached
:releasedran, and handed a value over - see Working on data in place
:failedexecute_unsafe! raised
:invalid_nodestructure or required inputs missing
:invalid_settingsvalidate_settings returned false
:invalid_resultvalidate_result returned false

execute! walks these stages:

  1. reset the per-run node log if the run changed;
  2. detect re-entry (check_cyclic) and warn instead of recursing forever;
  3. return immediately if the node is already :clean;
  4. mark :executing;
  5. execute parents recursively (execute_upstream);
  6. validate structure, required inputs (check_input_buffer) and settings;
  7. call execute_unsafe!;
  8. validate the result;
  9. store ready_ports and push outputs into the child buffers;
  10. clear the child buffers of the output ports this execution did not publish, so nothing is read as this turn's answer when it is the previous turn's;
  11. invalidate children (invalidate_downstream);
  12. mark :clean;
  13. release the producer of every handover input the node actually took.

Steps 1 and 13 are bracketed by the on_start and on_finish callbacks when they are set - see Watching a run below.

The four flags in parentheses come from ExecuteSettings:

execute!(w, id)                                                   # all flags on
execute!(w, id; settings = ExecuteSettings(; execute_upstream = false))
execute!(w, id; settings = ExecuteSettings(false))                # all flags off

execute! returns the vector of ports produced, or an empty vector when the node was rejected or failed - so an empty result is a signal to inspect getstatus.

Working on data in place

Nothing is copied on a connection. The value a producer publishes, the value in every consumer's buffer and the value in the producer's own cache are one object, and a MultiPort only builds a fresh vector around the same ones.

That makes the default rule short: a node must not modify what getinputdata hands it. A node that sorts, scales or appends to it in place changes what the producer believes it published - and the producer stays :clean, so the next run that does not recompute it hands the corrupted value back:

scheduler!(w)                        # сумма 12.0, верно
setsettings!(w, child, ...)          # потомок :dirty, родитель :clean
scheduler!(w; reset_mode = :none)    # сумма 24.0 — потомок считает на том,
                                     # что сам испортил на прошлом прогоне

:full and :soft hide this, because they mark every node :dirty and the producer recomputes. It bites exactly in the two paths whose point is not to recompute everything: reset_mode = :none, and an execute! that pulls a :clean parent.

When working in place is what you want - a large table that should not be copied at every step - declare handover = true on both ports of the connection, in their PortSpec, and take the input in the body with take!:

PortSpec("table", DataFrame, :table; handover = true)   # и у выхода, и у входа

function MetidaFlows.execute_unsafe!(node::DataNode{Trim})
    table = take!(node, :table)        # теперь таблица наша
    filter!(row -> row.value > 0, table)
    setdata!(node, :out, table)
    return setreadyports!(node, :out)
end

One keyword, two sides, and the rule between them runs one way. An output so declared is allowed to give its value away and may feed any input. An input so declared takes ownership and may be fed only by such an output - that is the pairing the engine checks when the connection is created.

The declaration is permission, not transfer. Publishing changes nothing: until somebody takes the value it is still shared, the producer keeps its cache and stays :clean, and modifying what getinputdata returned is the same mistake it is anywhere else. What moves ownership is take!.

So the transfer is recorded by what happened, not by what was declared. take! empties the buffer slot, the engine sees that slot go empty across the node's execution, and only then drops the producer's cached copy of that port and turns the producer :released. The producer's status therefore changes during the consumer's execution - a node never reaches into anybody else's state, and a value nobody took stays cached and republishable.

What this costs:

  • the output port takes exactly one connection, refused at creation otherwise: a second consumer would receive a value the first is entitled to overwrite;
  • once taken, the producer is :released rather than :clean, so it recomputes next run instead of republishing a value it no longer holds, and getdata on that port answers nothing;
  • an invalidation that reaches the node turns :released into :dirty like any other status, so the mark says "handed over on the last run", not "handed over at some point".

Taking is checked against the node's own specification, which is why it needs no access to the graph: by the time a node takes anything, the pairing was settled when the connection was made. Taking and then failing still counts - the value has left the buffer either way, so the release is made from finally.

:released answers two different questions differently, and that is the whole of it: to a consumer asking can I rely on you for the value already in my buffer it answers like :clean; to anyone asking do you have a cache to republish it answers like :dirty.

A handover port whose value nobody takes - because it has no connection, or because the consumer reads it the ordinary way - hands nothing to anybody. It is cached as usual and the node stays :clean.

Invalidation and caching

Caching is what makes incremental recomputation work: a :clean node returns its stored ready_ports without calling execute_unsafe! again. Everything that could make a cached result wrong therefore has to mark nodes :dirty.

invalidate_downstream! is the propagation primitive. Starting at a node it marks it :dirty, drops its cached outputs, deletes the child buffer entry belonging to each outgoing connection and recurses. Traversal stops at nodes that are already :dirty, since their subtree was invalidated earlier.

It is triggered by setsettings!, add_connection!, delete_connection!, replace! and by execute! itself.

reset! is the other direction: what you throw away between runs. It takes a level from RESET_LEVELS, and the levels are a ladder - each one does what the one before it does and more:

levelclears, on top of the level beforekeeps
:nonenothingeverything
:statusthe status, which becomes :dirtyeverything else
:softexec_n, the stop flagdata, ready_ports, every buffer, settings
:full (default)cached output data, ready_ports, the buffers of :feedback portssettings, the other buffers, the node log
:inputsevery remaining input buffersettings
:allsettings, the node log, execution_id; the status becomes :idlenothing - the node is as new

A workflow and a single node take the same levels and the same default, and reset!(model; level = L) is exactly a loop of reset!(node; level = L):

reset!(w)                      # инвалидация: настройки целы
reset!(w; level = :inputs)     # и входные буферы тоже снять
reset!(node; level = :all)     # узел как новый

mark_dirty! is not a level of that ladder. It is the primitive invalidate_downstream! is built from, and it keeps exec_n and the stop flag that even :soft clears, because a subtree that was merely invalidated has not stopped counting.

Two things on the ladder are worth saying out loud. :full clears the :feedback buffers and :inputs clears the rest, so :inputs is the level that leaves no buffer behind. And :all ends at :idle rather than :dirty, because a node with nothing in it has not been invalidated - it has been emptied.

Low-level buffer access - setinputbuffer!, invalidate_buffer!, push_buffer! - is available when you drive execution manually, but note that writing a buffer by hand bypasses invalidation.

A port that was not published to

A node need not publish every output port, and every gate in this package relies on that. The question is what the consumer of a port that was not published to sees - and the answer has to be "nothing", not "whatever was there last turn". execute! therefore calls invalidate_unpublished! right after push_buffer!: the consumer buffers of :normal connections leaving an unpublished port are cleared.

:feedback connections are left alone, because their buffers are the state of a loop - a gate that ends a run publishes only its :terminal ports, and the loop head's feedback buffers have to survive that. :error connections are left alone too: they latch a diagnosis until a handler reads it.

Conditional evaluation

A graph has no short-circuit inside a turn: both operands of a condition are nodes, and both are computed - insertion sort shows what that costs. But a computation can be made conditional, in two ways, and both rest on a producer publishing nothing:

Through nothing. The consumer declares the guarded port required = false and branches on its absence:

spec = NodeSpec("Maybe",
    [PortSpec("P", Int, :p; required = false), PortSpec("Q", Int, :q)],
    [PortSpec("Out", Int, :out)])

function MetidaFlows.execute_unsafe!(n::DataNode{Maybe})
    p = getinputdata(n, :p)
    setdata!(n, :out, isnothing(p) ? getinputdata(n, :q) : p)
    return [:out]
end

The node still runs; what it does changes. This is the cheap form, and the one to use when the guarded work is a choice rather than an expense.

Through a guard. Route everything the guarded subgraph needs through one node that either passes it on or publishes nothing:

MetidaFlows.execute_unsafe!(n::DataNode{Guard}) =
    getinputdata(n, :pass) ?
        (setdata!(n, :value, getinputdata(n, :value)); [:value]) : Symbol[]

Then the guarded node has no fed input at all: in ABW nothing enqueues it and in DAW it is not ready, so in both it ends the run :dirty, never executed. This is the form that actually saves the work - at the price of relaying, and on two conditions: the guarded node must have no other producer that keeps publishing, and nothing may consume its output unless the run is told to release such a consumer. By default a consumer of a node that never runs waits for a producer that stays :dirty, and waits forever - even through an optional port, because waiting is about the producer's status, not about the value. So the guard form suits a dead end: a :terminal port, a side effect, a branch whose result is read out of band. To merge a guarded branch back in, see release_optional below.

When the result has to come back into the computation - into a loop state, or a merge - the other way is to put the conditional inside the node that does the expensive work:

function MetidaFlows.execute_unsafe!(n::DataNode{MulIf})
    getinputdata(n, :pass) || return Symbol[]      # the multiplication is skipped
    setdata!(n, :out, getinputdata(n, :a) * getinputdata(n, :b))
    return [:out]
end

The node runs - which costs a flag check - and the operation does not. Its consumer reads nothing and knows the work was skipped. Modular exponentiation is built this way and measures what it saves.

Why the wait cannot simply be dropped

It is tempting to let isready not wait for the producer of an optional port at all. It is not sound in ABW: the queue order is not the author's to choose, so a consumer could run before the producer decides, read nothing, and be wrong on a turn where the value was coming. Measured on the exponentiation graph, 3^5 mod 7 comes out as 1 instead of 5, with no multiplication performed at all. The wait is what makes "the producer published nothing" distinguishable from "the producer has not run yet". What can be dropped is the wait for a producer that has already had its chance to run, which is what release_optional does, below.

Those two cases are what required distinguishes, and both schedulers now answer them the same way:

the portwhat happens
required, producer published nothingnot ready - the node does not run, stays :dirty
required, no connection at alla structural error - :invalid_node, see execution_node_validation
required = false, no value for any reasonthe node runs and reads nothing

The middle row used to differ: ABW did not consult required at all, so it ran the node and handed its body nothing.

Releasing a node blocked only by an optional port

The last row of that table is about a port with no value. It says nothing about when a run may conclude there is none - and by default a run concludes it only when the producer ran and stayed silent. A producer that was never executed at all leaves its consumer waiting, which is what confines the guard form to dead ends.

release_optional, off by default on both schedulers, adds the missing conclusion. A node held back only by required = false ports is run, reading nothing there:

scheduler!(w; release_optional = true)

The flag is not "stop waiting". It is "stop waiting where the producer has already had its chance", and each scheduler has exactly one place that guarantees that:

schedulerthe guarantee
DAWtopological order - when the traversal reaches the consumer, its producer has already run, failed, or been skipped
ABWan empty queue - nothing will execute again by itself, so a producer that has not produced by now never will

So in ABW the ordinary turn still waits, and the release happens only when the queue has run dry, after which the queue is served again; see release_optional_blocked!. A required port never releases a node.

Releasing is half of it. The other half is that the consumer's buffer may still hold an earlier turn's value: invalidate_unpublished! covers a producer that ran and published nothing, but nothing clears the buffer of a producer that did not run - mark_dirty_downstream! deliberately leaves input buffers alone, because in a cycle they are the loop state. So a released node has its stale optional buffers dropped first, by invalidate_stale_optional!. Measured on a guarded accumulator loop: without that step the sum comes out 26 instead of 18, because the previous turn's value is added a second time.

What the flag buys is a conditional branch rather than a conditional operation - a guarded subgraph whose result merges back in:

scheduler!(w)                              # the consumer waits forever: no result, no error
scheduler!(w; release_optional = true)     # the branch is skipped and the merge happens

On the exponentiation graph the guard form then becomes the cheaper of the two idioms: for n = 1024 the multiplication node is executed once instead of on all 12 turns, and the answer is the same. What it costs is that "no value" now also covers "the producer failed", so a failure upstream of an optional port becomes a nothing the consumer must handle rather than a node that does not run. That is why it is opt-in.

Schedulers

scheduler!(w)                    # DAW
scheduler!(w; maxiter = 5000)    # ABW
DAWABW
Ordertopological, via topological_sortreadiness queue
Cyclesrejected before executionnot detected up front
Per runreset! at reset_mode, :full by defaultthe same, where :full also clears the :feedback buffers
Required inputsenforcedenforced
Nodes executedevery node, at most onceonly nodes reachable from input-free nodes, any number of times

Both return true when the traversal finishes. That is not a success flag: individual nodes may still end up :failed or :invalid_*, so check getstatus when correctness matters.

In ABW, a node popped while a parent is still :dirty is dropped and re-queued later by that parent; isready implements the check. A node that has input ports but no incoming connection never becomes ready and stays :dirty.

The graph is built once per edit, not once per run

A DAW run needs three things from the structure - the graph, the answer to "is it cyclic", and a topological order - and none of them change between runs of an unedited workflow. Each is computed when asked for and cached in model.graph (see GraphCache), keyed by model.ver: a counter of structural edits. Repeated runs of an unedited workflow therefore do no graph work at all. An ABW run needs none of the three, so it is unaffected either way.

The three readers are makegraph, is_cyclic and topological_sort, and each returns the shared value the workflow holds, so treat all three results as read-only. Copy the graph before modifying one: a vertex added to the cached graph leaves the workflow describing a graph it does not have, and nothing reports it.

Edit a graph through the five editing functions

add_node!, delete_node!, add_connection!, delete_connection! and replace! raise model.ver, and that is the whole mechanism that tells the cache it is out of date. Nothing else raises it - settings, data, buffers, statuses and a run leave it alone, because none of them can change the graph.

Writing into model.nodes or model.connections directly is not supported. Those fields are reachable and nothing stops it, but ver stays where it was and the cache goes on answering from the structure it saw last. For a workflow assembled that way from new, that is the empty graph it was born with, and every symptom is silent:

w = Workflow(0; type = :DAW)
for (id, node) in other.nodes; w.nodes[id] = node; end        # ТАК НЕ НАДО
for (id, con)  in other.connections; w.connections[id] = con; end

makegraph(w)      # граф без вершин
is_cyclic(w)      # false — даже если цикл есть
scheduler!(w)     # true, не исполнив ни одного узла

Build it with the editing functions instead:

w = Workflow(0; type = :DAW)
a = add_node!(w, DataNode(MyNode, spec))
b = add_node!(w, DataNode(MyNode, spec))
add_connection!(w, a, :out, b, :in)

Two cases where that is not quite enough, and what to do instead:

  • copying a workflow, where the identifiers of the original have to survive. add_node! hands out its own from n_iter and cannot reproduce them, so go through the snapshot codec - workflow_to_dict then dict_to_workflow. It keeps the identifiers, rebuilds the indices and leaves the version right.
  • a direct write you cannot avoid. Raise the version yourself, in the same breath, and remember that refreshind! rebuilds the indices only:
w.connections[id] = con
refreshind!(w)              # индексы
w.ver += 1                  # кеш графа

Watching a run

The engine reports two moments per execution, through two callbacks on ExecuteSettings, or as keyword arguments of scheduler! which builds its own settings:

using MetidaFlows

struct Step <: AbstractNodeType end
MetidaFlows.execute_unsafe!(n::DataNode{Step}) =
    (setdata!(n, :out, something(getinputdata(n, :in), 0) + 1);
     MetidaFlows.setreadyports!(n, :out))

spec() = NodeSpec("Step", [PortSpec("in", Int, :in; required = false)],
                          [PortSpec("out", Int, :out)])

w = Workflow(1; type = :DAW)
a = add_node!(w, DataNode(Step, spec()))
b = add_node!(w, DataNode(Step, spec()))
add_connection!(w, a, :out, b, :in)

seen = Tuple{Symbol, Int, Symbol, Int}[]
scheduler!(w;
    on_start  = ev -> push!(seen, (:start,  ev.id, ev.status, ev.exec_n)),
    on_finish = ev -> push!(seen, (:finish, ev.id, ev.status, ev.exec_n)))
seen
4-element Vector{Tuple{Symbol, Int64, Symbol, Int64}}:
 (:start, 1, :dirty, 0)
 (:finish, 1, :clean, 1)
 (:start, 2, :dirty, 0)
 (:finish, 2, :clean, 1)

Each callback takes one NodeExecutionEvent, which carries the node id, the run_id of the run, and the status and execution counter as they were at that moment. The start fires as the engine takes the node up, before the :clean check and before validation, so every finish has exactly one start in front of it.

That is what makes the pair readable: exec_n rising across the pair means the node's own code ran, and the same number on both means it did not. A :clean node under reset_mode = :none reports a pair with no change:

scheduler!(w; reset_mode = :none,
    on_start  = ev -> println("start  ", ev.id, " ", ev.status, " n=", ev.exec_n),
    on_finish = ev -> println("finish ", ev.id, " ", ev.status, " n=", ev.exec_n))
start  1 clean n=1
finish 1 clean n=1
start  2 clean n=1
finish 2 clean n=1

What the engine does not do for you

Nothing is stored. The events are a stream: whatever the callback does not keep is gone, and the engine grows no buffer of its own. A collector is a closure over your own container, and a bound on it is yours to set - which is deliberate, because a loop in ABW reports one pair per execution, and a five-hundred-turn descent reports a thousand events.

Durations are not measured. Nothing in the event is a timestamp, because now() on every node is a system call in the hot path. A callback that wants elapsed time takes its own reading on both halves of the pair.

An exception from a callback is caught and written to model.log at level :error, so a broken callback does not fail a run. With SETTINGS[:logging] off it is not recorded anywhere, so a callback you are still writing is better tested with logging on.

Editing the graph from a callback is not allowed. It would raise model.ver and invalidate the cached execution order in the middle of the walk, and the rest of the run would mean nothing. The engine compares the version across the call and logs an error if it moved - it reports the damage, it cannot undo it.

A node the scheduler dropped reports nothing. In ABW a node is popped and put back whenever isready refuses it, and that never reaches execute!. The events describe executions, not queue traffic.

The cost when nobody is watching

Both callbacks default to nothing, and ExecuteSettings carries their types as parameters, so the default is an ExecuteSettings{Nothing, Nothing} and the dispatch that fires an event resolves to a method with an empty body. The event itself is built inside that method, so a run with no callbacks does not even assemble one.
