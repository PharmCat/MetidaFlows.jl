Reading and writing a node

Getters and setters. Most take a node, which getnode gives you from an identifier; the ones that are asked for often take a workflow and an identifier as well.

Exported

Available after using MetidaFlows. These are the public API in the narrow sense: the names you cannot build or run a graph without.

MetidaFlows.getinputdata — Function
getinputdata(node::AbstractDataNode, l::Symbol)
getinputdata(node::AbstractDataNode, l::Symbol, con::Int)

Read value from node input buffer.

The two-argument form depends on the port arity:

  • SinglePort: returns the buffered value, or nothing when the buffer is empty; more than one buffered value is an error.
  • MultiPort: returns a Vector of the buffered values, ordered by ascending connection id - that is, in the order the inputs were attached. The vector is freshly built, so a node may consume or reorder it without touching its own buffer. Use getinputconnections for the matching connection ids when a node needs to tell its producers apart.

The three-argument form returns the value written by connection con, or nothing when that connection has nothing buffered.

Both forms raise an error when l is not an input port of the node specification, and neither consumes or clears the buffer.

source
MetidaFlows.getinputconnections — Function
getinputconnections(node::AbstractDataNode, l::Symbol)

Connection ids buffered on input port l, ascending - the same order in which getinputdata returns the values of a MultiPort.

Needs no Workflow, so it is callable from execute_unsafe!, which is given only the node. The ids are what a node zips against its values when it has to tell its producers apart:

for (cid, v) in zip(getinputconnections(node, :ins), getinputdata(node, :ins))
    # settings[:role][cid] - the meaning the graph author assigned at build time
end

Raises an error when l is not an input port of the node specification.

See bufferkeys for how a custom buffer container reports its order.

MetidaFlows.setsettings! — Function
setsettings!(model::Workflow, id::Int, settings::Dict{Symbol, <: Any})

Apply new node settings and invalidate dependent nodes.

Settings are applied using setsettings_unsafe!, after which the target node and all downstream nodes are invalidated via invalidate_downstream!.

Notes

  • This function is the safe high-level entry point for mutating node configuration inside a workflow.
  • Settings are merged: only the keys present in settings are overwritten, the rest are kept.
  • The keys are not checked against the list in NodeSpec: that list is a declaration, and an unknown key is simply stored. Enforce what matters in validate_settings.

Returns

The node.

Public, not exported

Part of the public API, reached as MetidaFlows.name or brought in with import MetidaFlows: name. They are documented, and a breaking change to one of them moves the version exactly as a change to an exported name does. They are simply not put in your namespace, either because you add methods to them, because they are needed rarely, or because the name is too general to take over.

MetidaFlows.getexecn — Function
getexecn(model::Workflow, id::Int) -> Int

How many times the node has executed since its execution state was last cleared.

The counter lives in NodeState and is raised by execute! just before the node's own code runs, so a node that raised still counts as having executed. reset! zeroes it; reset!(model; soft = true) zeroes it too, since both forms reset the counter.

This is the cheapest way to ask what a run actually did: a node left :dirty below a failure has the same status as a node that was never reached, but a different exec_n. In a cyclic ABW workflow it counts turns.

Example

scheduler!(w)
getexecn(w, id)                 # 1 — узел исполнился один раз
scheduler!(w; reset_mode = :none)
getexecn(w, id)                 # 1 — чистый узел не пересчитывался

MetidaFlows.bufferkeys — Function
buffervalues(buffer)  -> Vector
bufferkeys(buffer)    -> Vector{Int}
buffersingle(buffer)

How the engine reads one port's buffer. The three are what a container may specialize, and PortBuffer - the default - specializes all three.

buffervalues and bufferkeys give the values and the connection ids ordered by ascending connection id; they are what getinputdata and getinputconnections return for a MultiPort, so the two line up position for position. buffersingle gives the one buffered value of a SinglePort, nothing when the buffer is empty, and raises when more than one connection has written - the generic form reaches it through the pair the iterator yields, which is worth avoiding in a container that stores its values contiguously (measured: a 200-node SinglePort chain runs 20 % faster for it).

The default works for any container keyed by connection id: it collects the keys, sorts them, and indexes. That is two allocations and a sort on every call, because a Dict cannot report an order it does not keep.

A container that does keep its keys in order can say so, and then the sort and one of the allocations go away:

MetidaFlows.bufferkeys(b::SortedBuffer)   = copy(b.cids)
MetidaFlows.buffervalues(b::SortedBuffer) = copy(b.vals)
MetidaFlows.buffersingle(b::SortedBuffer) = length(b.vals) == 1 ? b.vals[1] :
                                            isempty(b.vals) ? nothing :
                                            error("Multiple connections in single port")

Both must return a fresh vector in the same order: the node is free to sort, consume or empty what it is given, and must not reach the buffer through it. Returning b.vals itself would hand the engine's buffer back to the node.

MetidaFlows.get_parents — Function
get_parents(model::Workflow, id::Int)

Get parents (incoming connections of the node). Returns Vector of Tuple (inputport, parentid) for each incoming connection - one entry per connection, so a node reached through several ports appears several times.

An unknown id gives an empty vector.

See also get_children, which returns triples (outputport, childid, input_port).
