Types

The workflow, the node and everything a node is made of: ports, specifications, properties, state, the container supertypes and the audit events.

Exported

Available after using MetidaFlows. These are the public API in the narrow sense: the names you cannot build or run a graph without.

MetidaFlows.AbstractNodeType — Type
AbstractNodeType

Supertype of node behaviour tags. A user-defined node type is a singleton subtype used as the first type parameter of DataNode; execution and validation are attached to it through multiple dispatch:

struct MyNode <: AbstractNodeType end
 
function MetidaFlows.execute_unsafe!(node::DataNode{MyNode})
    setdata!(node, :out, 42)
    return [:out]
end

MetidaFlows.ExecuteSettings — Type
ExecuteSettings(; execute_upstream = true, invalidate_downstream = true,
                  check_cyclic = true, check_input_buffer = true)
ExecuteSettings(execute_upstream, invalidate_downstream, check_cyclic, check_input_buffer)
ExecuteSettings(all_flags::Bool)

Execution flags consumed by execute!:

  • execute_upstream - recursively execute parent nodes first;
  • invalidate_downstream - invalidate child nodes after successful execution;
  • check_cyclic - detect re-entrant execution of the same node (Ring detected);
  • check_input_buffer - require data on every required input port.

The single-argument form sets all four flags to the same value.

MetidaFlows.PortSpec — Type
PortSpec(name, datatype, label, ::T = SinglePort(); required::Bool = true,
         kind::Symbol = :normal) where T <: AbstractPortType

Specification of a node port.

Fields:

  • name::String - human-readable name of the port.
  • datatype::Type - Julia type of the port data (connection type checking).
  • label::Symbol - unique label used for referencing the port in code.
  • required::Bool - whether the port must have buffered data for execution.
  • kind::Symbol - how the schedulers treat connections attached to the port.

The optional positional argument selects the port arity: SinglePort (default) or MultiPort.

Port kinds

kindMeaning
:normalan ordinary data connection: isready waits for its producer and execution_node_validation requires a value when required
:feedbackinput ports only: closes a cycle and carries the value of the previous iteration. Not waited for, not required
:terminala slot for a result that is not meant to be connected. Connecting one is allowed but warns: the kind is a statement of intent, not a constraint
:errorreserved for error routing; must be required = false and its datatype must be a subtype of Exception

Constraints are checked at construction time. kind = :feedback on an output port is rejected by the NodeSpec constructor: a delay is a property of the consumer, not of the producer.

Only isready and execution_node_validation read the kind. Buffering, invalidation and serialization are identical for all kinds.

Example

PortSpec("value", Int, :val)                                  # required single port
PortSpec("items", Int, :vals, MultiPort())                    # multi-connection port
PortSpec("hint",  Int, :in; required = false)                 # optional port
PortSpec("state", Int, :prev; kind = :feedback)                # closes a cycle
PortSpec("report", DataFrame, :out; kind = :terminal)          # result slot
PortSpec("error", Exception, :err; kind = :error,              # error routing:
                                   required = false)           # both are mandatory

The arity is the only positional argument after the label, so a kind written positionally - PortSpec("p", Int, :p, :feedback) - is a MethodError, not a feedback port.

MetidaFlows.NodeSpec — Type
NodeSpec(name, input_ports, output_ports, settings)
NodeSpec(name, input_ports, output_ports)

Static description of a node interface: its ports and the settings keys it understands. The spec is the single source of truth - a port label that is not listed here is rejected by getdata, setdata!, getinputdata and by connection validation.

Fields:

  • name::String - human-readable node name.
  • input_ports::Vector{PortSpec}, output_ports::Vector{PortSpec} - port specifications.
  • settings::Vector{Symbol} - settings keys advertised through the node schema.
  • portmap::Dict{Tuple{Symbol,Symbol}, Int} - (direction, label) => port index, built by the constructor.

Ports are enforced, settings are not

The two lists are not symmetric, and it is worth knowing which is which. A port label that is not in the spec is rejected. A settings key that is not in settings is not: setsettings! merges whatever it is given, and the list is a declaration for settings_schema and for whoever builds a user interface over the node. If a setting is mandatory, or has to be of a particular type, say so in validate_settings - that is the only thing the engine checks, and a node that fails it ends :invalid_settings without executing.

Example

spec = NodeSpec("Filter",
    [PortSpec("Input table", DataFrame, :table)],
    [PortSpec("Filtered table", DataFrame, :table)],
    [:column, :threshold])

MetidaFlows.NodeConnection — Type
NodeConnection(output_id, output_port, input_id, input_port)

Directed edge from an output port of the parent node (output_id) to an input port of the child node (input_id).

Connections are stored under an integer identifier, and that identifier is also the key used inside the child input buffer - so several connections can feed one MultiPort without overwriting each other.

MetidaFlows.DataNode — Type
DataNode(type::Type{T}, properties, spec, settings::SettingsT, data::DataT, state::StateT, input_buffer::BufferT) where T <: AbstractNodeType where SettingsT where DataT where StateT where BufferT
DataNode(type::Type, id, status, position, spec; settings = Dict{Symbol, Any}(), data = Dict{Symbol, Any}(), state = NodeState(), input_buffer = Dict{Symbol, PortBuffer{Any}}())
DataNode(type::Type, spec; settings = Dict{Symbol, Any}(), data = Dict{Symbol, Any}(), state = NodeState(), input_buffer = Dict{Symbol, PortBuffer{Any}}())

Concrete workflow node.

The first type parameter is the user-defined behaviour tag (AbstractNodeType) on which execute_unsafe! and the validation hooks dispatch; the remaining four are the types of the containers, so a node can be backed by plain Dicts (the default) or by custom structs.

Fields:

  • properties::NodeProperties - id, status, position.
  • spec::NodeSpec - port and settings interface.
  • settings - configuration values (Dict{Symbol, Any} by default).
  • data - cached output values, keyed by output port label.
  • state - execution state (NodeState by default).
  • input_buffer - input_buffer[port label][connection id] = value (Dict{Symbol, PortBuffer{Any}} by default).
Changed in 0.3.0

BufferT is the type of the whole buffer container, not of the value inside it. Before 0.3.0 the field was declared Dict{Symbol, Dict{Int, BufferT}}, which fixed the container and left only the value type free; a node backed by a buffer struct was therefore impossible. Code that spelled the full DataNode{...} type out, or dispatched on its last parameter, has to be updated - nothing in this package did.

initbuffer! prepares the buffer against spec: for a dictionary it creates an empty entry for every declared input port, for a struct it checks that a field exists for each, and either way it rejects entries that are not input ports.

Example

node = DataNode(MyNode, spec)
id   = add_node!(workflow, node)

See AbstractNodeFields for what a container has to support, and nodebuffer for choosing one per node type.

MetidaFlows.Workflow — Type
Workflow{T <: WorkFlowType}

Container holding the nodes, the connections and the connection indices of a workflow.

Fields:

  • id, name - workflow identity.
  • nodes::Dict{Int, DataNode} - nodes by identifier.
  • connections::Dict{Int, NodeConnection} - connections by identifier.
  • incoming, outgoing - node id => [connection ids] indices.
  • n_iter, c_iter - monotonically increasing id counters; identifiers of deleted nodes and connections are never reused.
  • run_id - identifier of the current scheduler run.

  • audit_log - the graph change log; empty unless SETTINGS[:audit] is on, see AbstractAuditEvent.

Public, not exported

Part of the public API, reached as MetidaFlows.name or brought in with import MetidaFlows: name. They are documented, and a breaking change to one of them moves the version exactly as a change to an exported name does. They are simply not put in your namespace, either because you add methods to them, because they are needed rarely, or because the name is too general to take over.

MetidaFlows.AbstractAuditEvent — Type
AbstractAuditEvent

Supertype of the records in Workflow.audit_log: a change log of the graph in the order the edits happened.

Five concrete events, one per model-level mutator: NodeAdded, NodeDeleted, ConnectionAdded, ConnectionDeleted and SettingsChanged.

That set is the mutators that take a Workflow, which is also the boundary of what the log can see: setid! and setposition! are given a node and no model, so moving a node in an editor is not an edit this log records.

What it is not

  • Not an undo stack. SettingsChanged records which setting keys changed, not their values before and after: the log would otherwise carry a second copy of every value a user ever typed, into every snapshot.
  • Not a trace of execution. Running a graph is not an edit. The per-run log of a node is NodeState.log, and the workflow's is Workflow.log (LogMsg).
  • Not timestamped. The vector's order is the sequence, and it is the same on every machine; a wall clock would only add something that is not reproducible.

Recording is off by default - see Workflow and the audit keyword - and when it is on, nothing is ever dropped: the log is neither capped nor truncated by the engine. A change log with holes in it answers "did this happen?" with a maybe, which is worse than having none, so the switch is all or nothing. Trimming it, if a long editing session needs that, is the caller's business. Cascades fall out of the mutators: delete_node! deletes the node's connections through delete_connection!, so the log shows each ConnectionDeleted and then the NodeDeleted.

Implemented in 0.3.0

Until 0.3.0 this type had no concrete subtype and nothing was ever written to audit_log.

MetidaFlows.SettingsChanged — Type
SettingsChanged(id, keys) <: AbstractAuditEvent

Settings of node id were written by setsettings!. keys are the setting names that were passed, in sorted order - values are deliberately not recorded, see AbstractAuditEvent.

Sorted rather than as given: the caller passes a Dict, whose iteration order is not the insertion order, so recording them as they came would make the log differ between machines on identical edits.

MetidaFlows.WorkFlowType — Type
WorkFlowType

Supertype of workflow execution models. Concrete subtypes (DAW, ABW) parameterise Workflow and select the scheduler! implementation.

source
MetidaFlows.DAW — Type
DAW <: WorkFlowType

Data Analysis Workflow: a deterministic acyclic graph. Its scheduler rejects cyclic graphs, resets every node and executes the whole graph in topological order, each node exactly once per run.

source
MetidaFlows.ABW — Type
ABW <: WorkFlowType

Agent-Based Workflow: execution is driven by a readiness queue instead of a fixed topological order. Nodes without input ports seed the queue, and every executed node enqueues the children attached to its ready output ports.

Log record kept in Workflow.log and in the node execution state.

MetidaFlows.AbstractNodeFields — Type
AbstractNodeFields

Supertype of the node field containers: NodeState, AbstractNodeSettings, AbstractNodeData, AbstractNodeState, AbstractNodeInputBuffer.

A node's settings, data and state can be plain Dicts - the default - or purpose-built structs, so a workflow can be fully typed with no Dict anywhere. Subtypes of this type get the Dict-like interface the engine uses, over their own fields:

mutable struct FilterSettings <: MetidaFlows.AbstractNodeSettings
    column::Symbol
    threshold::Float64
    FilterSettings() = new(:none, 0.0)      # see `empty!` below
end

s = FilterSettings()
s[:threshold]           # getindex  -> getfield
s[:threshold] = 1.5     # setindex! -> setfield!  (mutable subtypes only)
keys(s)                 # (:column, :threshold)  -> fieldnames
haskey(s, :column)      # -> hasfield
get(s, :missing, nothing)
empty!(s)               # back to FilterSettings()

The protocol

These five methods are what the engine calls on a container, and all five come from this type:

methodmeaningneeded by
getindex(obj, f)getfieldgetdata, node bodies
setindex!(obj, v, f)setfield!, mutable onlysetdata!, setsettings!
keys(obj)fieldnameserror messages, introspection
haskey(obj, f)hasfieldsettings_to_dict
get(obj, f, default)field or defaultgetdata
empty!(obj)every field back to what the zero-argument constructor givesmark_dirty!, reset!

empty! is the only one with a condition: a struct has no "empty" state of its own, so the generic method rebuilds one with T() and copies its fields over. Give the struct a zero-argument constructor, or define Base.empty! yourself - NodeState does the latter. Without either, empty! raises and names the type, because the engine clears cached output data on every invalidation and cannot proceed.

Which container a node gets is decided by nodesettings, nodedata, nodestate and nodebuffer - specialize those on the node type and both hand-built and loaded graphs come out typed.

See also DataNode.

MetidaFlows.AbstractNodeInputBuffer — Type
AbstractNodeInputBuffer <: AbstractNodeFields

Supertype for an input-buffer container: the outer mapping from input port label to that port's buffer. Choose one per node type with nodebuffer.

A subtype needs one field per declared input port, named after the port and holding a container keyed by connection id - initbuffer! checks that on construction, because fields cannot be added later. The per-connection level stays an associative container: connection ids are handed out at runtime, so no struct can have a field per connection.

mutable struct CellBuffer <: MetidaFlows.AbstractNodeInputBuffer
    diag::PortBuffer{Int}
    up::PortBuffer{Int}
    left::PortBuffer{Int}
    CellBuffer() = new(PortBuffer{Int}(), PortBuffer{Int}(), PortBuffer{Int}())
end
MetidaFlows.nodebuffer(::Type{Cell}) = CellBuffer()

Getting buffer[:diag] off such a struct is a field access, where a Dict hashes a Symbol; the per-port containers are concretely typed, so what the engine reads out of them needs no boxing.

Reachable since 0.3.0

Until 0.3.0 the input_buffer field was declared Dict{Symbol, Dict{Int, BufferT}}, which fixed the container and left only the value type free, so a subtype of this type could not be passed to a node at all.

MetidaFlows.SETTINGS — Constant
SETTINGS

Package-wide settings, in one mutable table. The engine reads three keys from it; anything else you put there is yours.

MetidaFlows.SETTINGS[:audit]     = true    # вести журнал правок графа
MetidaFlows.SETTINGS[:logging]   = false   # не писать сообщения движка
MetidaFlows.SETTINGS[:log_limit] = 200     # и держать не больше 200
MetidaFlows.SETTINGS[:my_thing]  = "..."   # своё — читайте через `get`
keytypedefaultwhat it controls
:loggingBooltruewhether log! records anything
:auditBoolfalsewhether audit! records anything
:log_limitInt1000how many messages a log keeps; 0 means no limit

A value of the wrong type, or one of these three keys deleted, raises an error naming the key rather than failing somewhere inside a run.

The eviction policy, in one place

A log at its limit drops its oldest record to make room for the newest, so what a log holds is the most recent :log_limit messages. A log whose length equals the limit is therefore possibly truncated, and that is the only signal there is - the count of what was dropped is not kept. When the whole history matters, raise the limit or set it to 0; when nothing should be recorded at all, set :logging to false.

:log_limit bounds both logs that hold LogMsg: Workflow.log and a node's own node.state[:log]. It does not apply to the graph change log: audit_log is never capped and never evicts, because a record of an edit that may or may not be there cannot be used to tell what the graph went through. See AbstractAuditEvent.

These are process-wide

One table for every workflow in the process. Two graphs open at once cannot differ, and code that changes a setting has to put it back - a test that needs the audit log on, above all, or it changes what every later test sees.

MetidaFlows.NodeState — Type
NodeState()

Per-node execution state with dict-like field access:

  • exec_n::Int - number of times execute_unsafe! was entered since the last full reset. Incremented by execute! right before the node body runs, so a node rejected by validation leaves it unchanged while a failed node does not.

Zeroed by reset!(model) in every reset mode, by reset!(node) and by empty!(state) — but not by mark_dirty!, so invalidating a subtree does not lose the count. In a cyclic ABW run the counter therefore holds the number of loop turns, and a node may read its own node.state[:exec_n] inside execute_unsafe! as the current turn number;

  • ready_ports::Vector{Symbol} - output ports produced by the last successful execution (used by push_buffer!);
  • execution_id::UInt64 - id of the run that last touched the node;
  • log::Vector{LogMsg} - the node's own log, written by the node through log! and by nothing in the engine; cleared by empty!(state) and reset!(node), not by reset!(model); bounded by SETTINGS[:log_limit], oldest dropped first.

Reset in place with empty!(state).

MetidaFlows.PortBuffer — Type
PortBuffer{V}() <: AbstractDict{Int, V}

The container the engine puts under one input port by default: values keyed by connection id, kept in ascending key order.

That order is the contract getinputdata publishes for a MultiPort, so a container that already holds its keys sorted answers with a copy instead of collecting, sorting and hashing - see buffervalues. Two parallel vectors, binary search to place a write.

Why sorted and not insertion-ordered

An insertion-ordered container (OrderedDict and friends) would record the order in which producers finished, which is scheduling order and not wiring order. Measured on three branches of different length feeding one port, wired as connections [5, 8, 9]: the short branch publishes first, so insertion order is [9, 8, 5] and the values come out reversed. Worse, overwriting a key does not move it, so a second run inherits whatever the first run's schedule happened to be. Sorting by key is independent of when anything ran.

Cost against a Dict

Measured per read, with V = Any:

Dict{Int, Any}PortBuffer{Any}
build + one write + one read (a SinglePort)448 B / 84 ns192 B / 60 ns
read 2 values in order208 B / 256 ns48 B / 18 ns
read 1000 values in order24 584 B / 12 850 ns8 040 B / 857 ns

Writing is cheaper too at one connection per port, which is the common case, and the insert costs more only when a port has many connections and they arrive out of order.

It is an AbstractDict, so code that treated a port's buffer as a dictionary - buf[cid], get, haskey, iteration over pairs, length, isempty, empty!, delete! - keeps working unchanged.

MetidaFlows.NODE_REGISTER — Constant
NODE_REGISTER::Dict{String, Tuple{Type, NodeSpec}}

MetidaFlows.GraphCache — Type
GraphCache

The graph of a workflow, cached: the directed graph itself and, derived from it, whether the graph is acyclic and a topological order of its nodes.

Held by Workflow in its graph field and never built by hand. Read it through makegraph, is_cyclic and topological_sort, each of which recomputes its own part when that part is out of date.

Fields

  • graph, is_cyclic, topological_sort - the three cached values.
  • ver, ic_ver, ts_ver - the Workflow.ver each of them was computed at. A value is current when its version equals the workflow's, so the three are refreshed independently: asking whether the graph is cyclic does not pay for a topological sort.

Staleness

Workflow.ver is raised by the four functions that edit a graph, and only by them, so a cached value is stale exactly when the structure changed through them.

A new workflow starts at version 0 with all three values already set - the empty graph, false, and an empty order - which is what an empty workflow's answers are, so nothing is computed until the first edit. The cache is therefore correct for as long as every edit goes through the editing functions, and silently wrong as soon as one does not: see Editing the graph in Workflow.
