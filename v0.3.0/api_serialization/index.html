Serialization and schemas

Snapshots of a workflow, the closed value codec, and the schemas a graph editor reads.

Public, not exported

Part of the public API, reached as MetidaFlows.name or brought in with import MetidaFlows: name. They are documented, and a breaking change to one of them moves the version exactly as a change to an exported name does. They are simply not put in your namespace, either because you add methods to them, because they are needed rarely, or because the name is too general to take over.

MetidaFlows.settings_schema — Function
settings_schema(node::AbstractDataNode) -> Dict

Description of the node settings for a user interface.

The engine fills in "settingslist" — a copy of spec.settings, that is the keys the node understands — and then calls settings_schema_usermod!, where a node type adds types, defaults, labels and allowed values.

Example

settings_schema(DataNode(FilterRows, filter_spec))
# Dict{String, Any}("settingslist" => [:column, :threshold])

See also node_schema for the node as a whole.

source
MetidaFlows.settings_schema_usermod! — Function
settings_schema_usermod!(d, node::AbstractDataNode)

Describe the settings of a node type, so an interface can render a form for them. Specialize it per node type; the default does nothing.

d arrives already holding "settingslist". Add to it — by convention under the key "schema", one entry per setting.

Mutate d: the return value is discarded. A method that builds a fresh dictionary and returns it has no effect.

The engine never reads the contents of "schema" and passes it through untouched, so the keys below are a convention shared with the interface rather than a format the package enforces: "type", "default", "description", "required", "options", "min", "max", "pinned" (show on the node body), "source" ("upstream", "user", "none").

Example

function MetidaFlows.settings_schema_usermod!(d, node::DataNode{FilterRows})
    d["schema"] = Dict{String, Any}(
        "column" => Dict{String, Any}(
            "type"        => "Symbol",
            "description" => "Column to compare",
            "required"    => true,
            "options"     => Symbol[]),
        "threshold" => Dict{String, Any}(
            "type"        => "Float64",
            "default"     => 0.0,
            "description" => "Keep rows whose value is greater than this",
            "required"    => true,
            "min"         => 0.0))
    return d
end

The method receives the node, so the description may depend on its current settings. For choices that only a producer knows — the columns of a file the parent node will read — combine the schema with getinputmeta on the caller's side.

Notes

  • Keep the executable check in validate_settings: a schema says what an interface should offer, not whether the node may run.
  • Prefer JSON-safe values. A function encodes as a meaningless string, and a Type is safer written as "Float64" than as Float64.

MetidaFlows.node_schema — Function
node_schema(node::AbstractDataNode) -> Dict

Description of a whole node for a user interface: its ports and its settings form.

The engine fills in "spec" (spec_to_dict) and "settings_schema" (settings_schema), and then calls node_schema_usermod!, where a node type adds presentation data.

Example

sort(collect(keys(node_schema(DataNode(FilterRows, filter_spec)))))
# ["settings_schema", "spec"]

MetidaFlows.node_schema_usermod! — Function
node_schema_usermod!(d, node::AbstractDataNode)

Describe the node itself — where it belongs in a node palette and how it is presented. Specialize it per node type; the default does nothing.

d arrives already holding "spec" and "settings_schema".

Mutate d: the return value is discarded.

Use this for presentation and grouping, and settings_schema_usermod! for the settings form.

Example

function MetidaFlows.node_schema_usermod!(d, node::DataNode{FilterRows})
    d["section"]     = "Tables"           # node palette section
    d["groupname"]   = "Filtering"        # group within that section
    d["color"]       = "#8b5cf6"
    d["icon"]        = "filter"
    d["description"] = "Keeps rows whose value exceeds a threshold."

    # the method sees the node, so the caption may depend on its settings
    col = get(node.settings, :column, nothing)
    d["caption"] = col === nothing ? "not configured" : "filter on $(col)"
    return d
end

MetidaFlows.AUDIT_EVENT_NAMES — Constant
AUDIT_EVENT_NAMES

The names audit_event_to_dict writes and dict_to_audit_event accepts. A closed set: a name outside it is an error, and nothing read from a file is resolved to a type.

MetidaFlows.audit_event_to_dict — Function
audit_event_to_dict(e::AbstractAuditEvent) -> Dict{String, Any}

One record of the graph change log as a JSON-serializable dictionary, tagged by "event" with one of AUDIT_EVENT_NAMES.

Port labels and setting keys are written as plain strings rather than through the value codec: a change log is read by people as often as by programs, and "a" says as much as {"t": "Symbol", "v": "a"}.

See also dict_to_audit_event.

MetidaFlows.dict_to_audit_event — Function
dict_to_audit_event(d::Dict{String}) -> AbstractAuditEvent

Rebuild one change-log record from the dictionary audit_event_to_dict produced.

d["event"] must be one of AUDIT_EVENT_NAMES; each is constructed explicitly from its own fields, so a file cannot name a type to build or a field to fill. Port labels and setting keys are accepted as String or Symbol, like the rest of the loader.

MetidaFlows.SNAPSHOT_FORMAT_VERSION — Constant
SNAPSHOT_FORMAT_VERSION

The snapshot format this version of the package writes, and the newest it reads.

workflow_to_dict stamps it into every snapshot under "format_version", and dict_to_workflow refuses a file whose stamp is higher than this number: a format from the future may mean things this code does not know. A lower stamp, and a file with no stamp at all, are read as the formats they are.

So a snapshot travels forward between versions, never backward.

MetidaFlows.value_to_dict — Function
value_to_dict(x)

Write a single value in a form a text format can carry.

nothing, Bool, Int64, Float64 and String are returned as they are. Everything else becomes a dictionary with a "t" type tag: Symbol, Char, Tuple, Vector (with an "e" element type tag), Dict (with a "k" key type tag) and the numeric types listed in VALUE_TYPES.

A value of any other type raises an error naming the type. Define settings_to_dict_usermod! for the node type to serialize it yourself.

See also dict_to_value.

source
MetidaFlows.dict_to_value — Function
dict_to_value(x)

Read back a value written by value_to_dict.

A tagged dictionary is rebuilt through the VALUE_TYPES table, so an unknown tag raises an error instead of being resolved: a type named in a file is never turned into a type object.

MetidaFlows.settings_to_dict — Function
settings_to_dict(node::AbstractDataNode)

Settings values of a node, keyed by setting name.

Only the keys declared in node.spec.settings are written; values go through value_to_dict. The function then calls settings_to_dict_usermod!, which a node type can specialize to write a value the codec cannot.

This is not the settings schema — see settings_schema for that.

See also dict_to_settings!.

MetidaFlows.dict_to_settings! — Function
dict_to_settings!(node::AbstractDataNode, d)

Put settings values from d into node.

Only the keys declared in node.spec.settings are read, so a file cannot inject a setting the node does not know. Values go through dict_to_value, then dict_to_settings_usermod! is called, and the result is written with setsettings_unsafe! — the node is :dirty right after loading, so there is nothing to invalidate.

See also settings_to_dict.

MetidaFlows.node_state_to_dict — Function
node_state_to_dict(node::AbstractDataNode)

Execution state of a node that a later run cannot recompute: the contents of its :feedback input buffers, keyed by port label and then by connection id.

Normal input buffers are not written. A normal buffer is filled by its parent within the same turn, and isready does not let a node run until every normal parent is :clean, so re-running refills it. A feedback buffer is the only value that crosses a turn boundary: its producer sits downstream and has not run yet when the turn begins.

exec_n is not written either, because reset! zeroes it on any resumed run. An algorithm that needs its own iteration counter carries it through a feedback port, and that counter is saved here.

See also dict_to_node_state!.

source
MetidaFlows.dict_to_node_state! — Function
dict_to_node_state!(node::AbstractDataNode, d)

Put feedback buffer contents from d back into node.

Each value is converted to the datatype the port declares in the registered spec, which both restores a concrete element type a text format had flattened (Vector{Int} from a plain array) and checks the value against the port. A port that is missing from the spec, or is not of kind :feedback, is an error.

See also node_state_to_dict.

MetidaFlows.workflow_to_dict — Function
workflow_to_dict(w::Workflow; values::Bool = true, state::Bool = false) -> Dict

Convert workflow to dictionary representation, ready to be serialized to JSON.

Keys: "format_version", "id", "name", "n_iter", "c_iter", "nodes", "connections", "incoming", "outgoing".

values writes the current settings values of every node, so the result is a workflow that can be loaded and run. state adds the contents of :feedback input buffers, which turns the result into a checkpoint of a run in progress - see node_state_to_dict and resume with reset_mode = :soft.

Notes

  • "nodes" and "connections" are keyed by stringified identifiers, while "incoming" and "outgoing" keep integer node ids.
  • Inside a node, "settings" holds the settings schema (settings_schema) and "settings_values" holds the values (settings_to_dict).
  • run_id, logs and cached output data are never included. Cached data is not needed: a loaded node is :dirty and recomputes.
source
MetidaFlows.dict_to_workflow — Function
dict_to_workflow(d::Dict{String}; usermode::Bool = false,
                 check_connection::Bool = true,
                 check_connection_throw_error::Bool = true) -> Workflow

Rebuild a workflow from the dictionary workflow_to_dict produced.

Every node type named in d must be registered first (register_node!): the file names a type, the register decides whether it may be built. Loading executes nothing - no user code runs, and no type is resolved from a string.

Settings values and feedback buffer contents are restored when the file carries them; see dict_to_node. Statuses are not: every loaded node is :dirty, so a loaded workflow recomputes. To continue an interrupted run instead of starting it over, call scheduler!(w; reset_mode = :soft).

usermode is passed to dict_to_node. check_connection runs check_connection_validity on every connection, and check_connection_throw_error decides whether a connection that does not validate is an error (the default) or is silently dropped - a graph that lost an edge computes something else, so prefer the error.

Notes

  • Every node key must match the "id" inside its "properties", and ids must be unique; either mismatch raises, naming the key.
  • n_iter and c_iter are raised to the largest id actually loaded, so the next add_node! or add_connection! cannot overwrite something the file brought in.
  • A snapshot with a "format_version" newer than SNAPSHOT_FORMAT_VERSION is refused; one without the key is read as version 1.
source
MetidaFlows.dict_to_node — Function
dict_to_node(d::Dict{String}; usermode = false) -> DataNode

Rebuild one node from the dictionary node_to_dict produced.

The node type and its spec come from NODE_REGISTER, looked up by the "type" string; the "spec" section of the file is not used. Settings values ("settings_values") and feedback buffers ("state") are restored when present - see dict_to_settings! and dict_to_node_state!. The node comes back :dirty whatever status the file carries, and without cached output data.

Its containers come from nodesettings, nodedata, nodestate and nodebuffer, so a node built from typed structs is loaded as the same typed node rather than falling back to Dicts. Nothing about the containers is read from the file: like the type and the spec, they are decided by the running code.

With usermode = true the spec is rebuilt from the file by dict_to_spec, which you define yourself; the type still comes from the register. This lets a snapshot carry a spec the register does not have.

MetidaFlows.dict_to_spec — Function
dict_to_spec(d::Dict{String}) -> NodeSpec

User-defined inverse of spec_to_dict, used only by dict_to_node with usermode = true. The package ships no method: a spec is normally taken from NODE_REGISTER, which is what keeps a snapshot from describing a node the running code does not have.

Define it if you need snapshots to carry specs:

function MetidaFlows.dict_to_spec(d::Dict{String})
    NodeSpec(d["name"], my_ports(d["input_ports"]), my_ports(d["output_ports"]),
             Symbol.(d["settings"]))
end

Resolve nothing from the file into a type or a function: a snapshot is data.
